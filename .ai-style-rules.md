## File Anatomy and Boundaries

- Keep each new module focused on one responsibility. Follow the approved `engine/` split rather than reproducing either legacy application file.
- In new Python modules, use this order when applicable: module docstring, `from __future__ import annotations`, standard-library imports, third-party imports, local imports, public constants/types, public functions, private helpers.
- Put UI configuration and presentation constants in UI modules. Put biological definitions and scientific calculations in `engine/`.
- `engine/` may contain Python standard-library code and approved scientific/data dependencies. It must never import Streamlit, Tkinter, Plotly, PyQt, CSS, HTML, or UI color constants.
- Streamlit adapters collect and validate inputs, call named engine APIs, convert engine errors into concise messages, and render returned data. Render functions must not calculate scientific results.
- The engine is the single source of truth for codon tables, mutation construction, exact tracking, sampled tracking, category analysis, denominators, and pure summaries.
- New filenames use lowercase `snake_case` and contain no spaces. The mandated parent directory name `final code/` is the sole existing exception.
- Every source, test, fixture, asset, configuration, dependency, build, and deployment artifact required by the application belongs under `final code/`.

## [Naming & State-Control Rules]

- Use `snake_case` for Python functions, methods, parameters, variables, modules, and filenames.
- Use `UPPER_SNAKE_CASE` for module constants and immutable lookup definitions.
- Use `PascalCase` for classes, dataclasses, exceptions, and `unittest.TestCase` subclasses.
- Prefix private helpers with a single underscore. Keep public engine names descriptive and scientific rather than UI-oriented.
- Preserve established scientific names and labels such as `start_codon`, `start_aa`, `stop_gen`, `per_gen_*`, `start_to_fin`, `total_start_copies`, “Exact probability,” “Sampled copies,” and the five category labels.
- Use explicit state/control names such as `display_mode`, `view_mode`, `selected_codon`, `selected_trait`, `no_more_basis`, `cumulative_stops`, and `state_after_*`. Boolean names should read as predicates, for example `hit_stop`, `show_*`, `is_*`, or `has_*`.
- New public engine functions require parameter and return type hints. Private helpers should also be typed when their contract is not obvious.
- New multi-field result APIs use named `@dataclass` models. Positional legacy tuples exist only in compatibility adapters with explicit conversion methods.
- Prefer explicit inputs and returned state. Do not introduce new mutable module globals. The sampled compatibility path is the exception: preserve the current module-level `random` behavior until a separately approved change.
- Preserve dictionary insertion order, record key order, DataFrame column/index/dtype/row order, generation labeling, and empty-schema behavior where compatibility fixtures cover them.

## Error Handling

- Engine code raises explicit, domain-appropriate exceptions with concise messages. Prefer `ValueError` for invalid scientific/input values and dedicated `PascalCase` exceptions only when callers need distinct handling.
- Do not catch broad `Exception` in new engine code unless adding context and immediately re-raising. Never silently convert a scientific failure into an empty or partial result.
- Streamlit adapters catch expected engine/input errors, call `st.error(...)` with concise actionable wording, and stop the current render path with `st.stop()` when continuing would be invalid.
- Keep validation messages consistent with the existing UI: state what is wrong and provide one short correction example where useful.
- Diagnostics raise `AssertionError` with observed and expected context. A passing diagnostic prints a stable, readable `PASS <case>` line.
- Tests use `unittest` assertions and `subTest` for compact case matrices. A mismatch must fail; never weaken a fixture or tolerance merely to make a test pass.

## Scientific and Compatibility Rules

- Preserve the 64-codon table, the 61 ordered sense codons, and stops `TAA`, `TAG`, and `TGA` exactly.
- Preserve amino-acid names, category membership, probability presets, substitution mapping, scientific labels, and all result meanings.
- Exact same-process comparisons must preserve `float.hex()` values and floating-point iteration order. Reviewed external fixtures may use only their explicitly documented tolerances.
- Preserve sampled mutation-position/base-choice call order, seed behavior, per-copy record order, path contents, early-stop behavior, copy numbering, and final `random.getstate()`.
- Every fraction or percentage must have an explicit numerator, denominator, and zero-denominator rule matching the approved Blueprint.
- Preserve conservation behavior: surviving mass/count plus cumulative stopped mass/count equals the starting population within the defined test tolerance.
- Keep exact and sampled modes visibly and semantically distinct.
- Phase 1 compatibility adapters preserve legacy signatures, defaults, concrete containers, tuple lengths, nested order, and UI behavior while new engine consumers use named results.

## UI, Accessibility, and Visual Rules

- Preserve existing Streamlit labels, widget order, keys, defaults, query bindings, cache behavior, chart/table surface, and interaction semantics unless an approved UI task changes them.
- Keep the existing light palette and category colors defined by `.streamlit/config.toml` and the web exemplar.
- Retain visible focus behavior, the “Skip to main content” link, semantic status markup, `aria-live`, decorative `aria-hidden`, and reduced-motion handling.
- Use concise headings, captions, validation messages, and scientific descriptions. Do not replace precise domain labels with generic product language.
- Keep Plotly construction and UI colors in presentation modules. The engine returns data, not figures or styling decisions.

## Testing and Change Discipline

- Run all implementation and verification commands from `final code/` after the Phase 1 baseline.
- Add focused `unittest` coverage beside each extracted engine responsibility before consumer cutover.
- Compare legacy and engine exact results in the same process; compare both sampled output and final RNG state.
- Treat both diagnostic scripts and both JSON fixtures as frozen oracles. Do not edit or regenerate them during Phase 1.
- Preserve readable failure output that identifies the invariant, case, and observed mismatch.
- Before editing an existing Phase 1 file, follow the Blueprint's direct-mode manifest, hash, backup, rollback, and execution-log requirements.
- Before every application-code edit, make a short compliance declaration naming the golden exemplar being followed and the relevant DONTs being avoided.

## [DONTs]

- Do not copy the monolithic file structure from `category_tracking.py`.
- Do not duplicate codon tables, amino-acid property tables, probability presets, mutation matrices, or simulation algorithms.
- Do not add scientific calculations, denominators, convergence rules, or mutation loops to render functions.
- Do not use positional tuple indexes in new APIs or new consumers; confine legacy tuple access to compatibility adapters and tests.
- Do not change denominators, zero behavior, RNG order, dictionary/record order, or floating-point iteration order during refactoring.
- Do not import Streamlit, Tkinter, Plotly, PyQt, CSS, HTML, or UI colors from engine modules.
- Do not let engine code display UI messages or let UI code swallow engine failures.
- Do not modify root research files or import them as runtime dependencies from the completed application.
- Do not place application files outside `final code/`.
- Do not create new filenames containing spaces.
- Do not redesign the UI, rename entry points, optimize algorithms, aggregate sampled paths, inject a new RNG, or add future infrastructure during Phase 1.
- Do not regenerate golden fixtures from tests, edit the frozen diagnostic, relax exact comparisons, or weaken tolerances after a failure.
- Do not treat `category_tracking.py`'s lack of typing, broad exception handling, embedded presentation, or giant classes as inherited style.

## Intentional Evolution Decisions

- The untyped legacy scientific surface evolves to typed public engine functions.
- Positional result tuples evolve to named dataclasses, with tuples retained only at compatibility boundaries.
- Mixed UI/scientific modules evolve to a UI-independent `engine/` plus thin UI adapters.
- Engine failures evolve to explicit exceptions; UI adapters retain concise user-facing messages.
- The legacy monolith evolves to focused modules without changing scientific or Streamlit behavior.

These decisions resolve the strong scan conflicts and are deliberate rules, not inconsistencies to copy.
